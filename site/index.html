Every version the catalog knows

Porting is the bottleneck, and here is exactly what it takes

A browser client is the real game with the parts a browser does not have replaced: windowing, OpenGL, audio, networking and the filesystem. That replacement layer is per-version work — it is why this catalog marks most versions queued instead of pretending they build. The pipeline around it is done: discovery, verdicts, acquisition, build orchestration, catalog and this page.

What a new version needs

  • a version profile in the engine (which classes to replace, which lists they belong in)
  • the client jar and asset index, fetched at build time into work/ — never committed
  • a TeaVM compile of the whole client, then a single-file package
  • the platform checks: WebGL 2 present, audio context, worker messaging, pointer lock

The commands, as the updater prints them

python3 tools/update.py --write
python3 tools/plan.py --kinds release,snapshot

Everything is fetched into work/ and built into dist/; neither is committed, and this repository contains no game files at all.

How this works

  • Discovery — tools/versions.py reads Mojang's version list and classifies every version (release, snapshot, old beta/alpha).
  • Verdict — tools/plan.py asks ports.json which engine can handle it: build (an engine has a profile), reuse (an engine publishes a client), or needs-port (nobody has written that version's browser layer).
  • Acquire — tools/acquire.py fetches the client jar and asset index into work/, verifying checksums.
  • Build — the engine compiles it (for the modern releases: Gaius, official client bytecode → WebAssembly).
  • Catalog — tools/update.py writes the state and this page's manifest, and queues the versions that need a port.

This repository hosts no Minecraft files: it holds code, and the page links clients where their own projects publish them. Builds fetch the game at build time and keep it in work/.
