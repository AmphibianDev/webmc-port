# Java 21 and 25 in a browser: what exists, what it costs, and the route this project takes

The question was "make a loader that runs up to Java 25 in the browser, so the launcher supports the
latest snapshot". This is the answer, with the evidence, because the honest version of that answer is
more useful than an optimistic one.

**Short version: no shipped browser JVM runs Java 21+, and one open-source route does.** CheerpJ - the
JVM this project already uses - stops at Java 17, and its own team says a Java 21 runtime is "planned
for later this year" as of 4.3 (April 2026). What does exist, on GitHub, is **OpenJDK compiled to
WebAssembly**: the `openjdk21` recipe in `wangyenshu/recipes` (emscripten-forge) with its
`openjdk21-kit` launcher. That is a real JVM with a real class loader in a page - which is the only
thing that can give Fabric *at play time* on a modern version. It has three costs, all named below.

## The four routes, measured

| Route | Java ceiling | Class loader (i.e. Fabric) | Speed | State today |
| --- | --- | --- | --- | --- |
| **CheerpJ** (in the page) | **17** - `cheerpjInit({version: 17})` | yes, a real JVM | good (JIT to JS/wasm) | 1.0 - 1.12.2 work; 1.13+ needs our JS LWJGL 3; Fabric reported hanging (below) |
| **OpenJDK Zero → wasm32** (in the page) | **21** now, 25 by porting the recipe | yes, a real JVM | **slow**: interpreter only, no JIT for wasm32 | recipe, kit and link script exist; no Minecraft build yet |
| **AOT compile** (TeaVM, what Gaius and our workspace do) | any (it is a compiler, not a runtime) | **no** - mods are baked at build time | fastest | 26.2/26.3 build today; this is how the newest snapshots can run this week |
| **CheerpX** (a Linux VM in the page) | whatever the guest installs | yes | emulated x86, then a real JVM on top | not measured here; the heaviest of the four |

Two facts decide everything else:

* **Java version is a hard wall per route.** A 26.x client is class file 69 (Java 25), and no runtime
  that tops out at 21 will load it. 44 + javaVersion is the rule, and it is in
  `tools/aot_profile.py` so the pipeline can say which route a version needs from its own metadata.
* **Mods need a class loader.** Fabric's whole mechanism is transforming bytecode as classes load, so
  it needs a VM that loads classes at play time. A compiled client has none - which is why on the AOT
  row mods go in *before* the compile, applied by a real Fabric Loader running in the build. That is
  already implemented in this project (`mods/loader.py`, `mods/build_modded_workspace.py`,
  `mods/loader-src/loader-mod`).

## The Fabric question, answered with a citation

There is an open report that **Fabric Loader's boot hangs inside its ASM transformation under CheerpJ**
(`leaningtech/cheerpj-meta#231`, July 2026, with a minimal reproduction at
`xuishimm/cheerpj-fabric-hang-repro`). It hangs *before* LWJGL is touched - so it is not the graphics
shim's fault - and the vendor's reply is that Minecraft 1.16.5 "cannot work in any case since it depends
on LWJGL3, which cannot yet be compiled to WebAssembly via our toolchains", and that they will not look
at the hang in the short term.

So the project's plan no longer promises Fabric wherever a JVM exists. Every plan now carries a
`caveats` list, and the launcher shows it before the play button:

* on the CheerpJ row: Fabric is unproven, vanilla is not;
* on the shim row: the same report, plus the missing LWJGL 3;
* on the AOT row: mods are applied at build time, and only mods that survive ahead-of-time compilation
  bake in at all.

## What the open-source route actually gives us

`openjdk21` (emscripten-forge recipe, OpenJDK 21.0.10, Zero interpreter, built with `x11-wasm` for
AWT/Swing) plus `openjdk21-kit` (launcher, link script, page shell) means:

* a **real JVM**: `System.loadLibrary`, JNI, reflection, class loading, and therefore Fabric's mixins.
  Threads are real (pthreads + `SharedArrayBuffer`; the demo pages ship a COOP/COEP service worker so a
  static host can serve it).
* **native methods are static symbols.** There is no dynamic loader: `os::dll_lookup` is answered from a
  table named `emscripten_static_symbols`, generated by `gen-symbols.sh` from the archives you link in.
  That is the same idea as this project's CheerpJ natives (`cheerpjInit({natives: {...}})`) and the same
  idea as the loader's own report native - a name → implementation table - so the shape is already
  familiar in this repository, and `tools/lwjgl3_surface.py` already measures exactly which names are
  needed (458 members across 1.13 - 1.20.4, from real clients).
* **the graphics stack exists in emscripten.** `-sUSE_GLFW=3` (GLFW 3 on the canvas, with input),
  `MAX_WEBGL_VERSION=2` (GLES 3 emulated on WebGL 2, which is why 1.13+ maps so well onto WebGL2), and
  `libal` (OpenAL) is a system library. What is missing is the JNI layer mapping LWJGL's expected
  symbols onto those three - C work, mechanical, and *ours* to generate from the measurement.
* **a JDK 25 port is a version bump** of a recipe that already exists, not a research project: Zero
  builds on any platform the C toolchain reaches, and the patches in that recipe are about the C
  library and AWT, not about the Java version.

What it does not give: speed. Zero is an interpreter, so the compiled rows stay ahead of it - this is
the route for *correctness and mods*, not for frames per second. Say so on the card, not in a footnote.

## The order this lands in

Each step is verifiable, and the first two do not depend on the runtime existing at all.

**The AOT row (this is what "supports the latest snapshot" means today):**

1. **A version profile for any version, including the newest snapshot** - done:
   `tools/aot_profile.py` reads Mojang's document (java, sha1s, asset index), reads `version.json` out of
   the client jar (protocol, world, pack versions - no JVM needed), computes the class file version, and
   copies the *port's own* fields from the nearest existing profile while saying out loud which ones
   those were. `tests/test_aot_profile.py` pins the split.
2. **A loading screen that looks like the game** - done: `site/boot/shell.html` reproduces what the game
   itself draws (black, centred progress text, the game's 200x2 bar, its GUI scale, a pixel shadowed
   font), and `tools/aot_shell.py` puts it in front of a compiled client, removes that client's own
   splash by id, and hands over on the first OpenGL draw call - so no engine has to cooperate.
3. **Fabric mods, baked** - already implemented here, and the plan now says so instead of implying
   runtime mods.
4. Then one build per version, which is the 45-minute job in `build-client.yml`; a snapshot needs a
   profile (step 1) and whatever source overrides that version's client needs.

**The wasm-JVM row (this is what "a loader that runs Java 25" means):**

5. Build the JDK 21 wasm runtime from the recipe (`pixi`/`rattler-build`, published to a conda channel
   for wasm32), link it into a page with the kit, and prove `java -version` in a browser.
6. Port the recipe to JDK 25, and prove a class file 69 loads.
7. Generate the LWJGL 3 JNI layer in C from the measured surface, over emscripten's GLFW 3 + GLES 3 +
   OpenAL, and prove a first frame (the same milestone the CheerpJ shim is chasing, on a different
   runtime - and this time the native call path is `ffi_call` into wasm, not a JS bridge).
8. Put **our own loader** on its classpath: `webmc.loader.WebMcLoader` is Java 8 bytecode, so a Java 25
   JVM loads it unchanged, and the link kit takes a classpath and a main class - which is exactly the
   interface it needs. Then Fabric Loader, then a mod jar.
9. Only then: is it fast enough to be worth offering next to the compiled row? Measure before claiming.

## What this project will not do

* **No streaming.** A session on a server is a different product, and running one on CI is what got an
  earlier account suspended.
* **No prebuilt clients from other projects.** Linked where they live, never copied.
* **No pretending.** A route with no build is not offered as playable: the wasm-JVM engine is in
  `ports.json` with `"enabled": false` and its three blockers written down, so the plan can explain the
  route without promising it.
* **No game files in the repository**, on any of these routes: the client is fetched at build time by
  the person building, and a built client is published as a download rather than served as a page (see
  `COMPLIANCE.md`).
