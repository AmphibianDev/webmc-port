# Java 21 and 25 in a browser: what exists, what it costs, and the route this project takes

The question was "make a loader that runs up to Java 25 in the browser, so the launcher supports the
latest snapshot". This is the answer, with the evidence, because the honest version of that answer is
more useful than an optimistic one.

**Short version: no shipped browser JVM runs Java 21+, and one open-source route does.** CheerpJ - the
JVM this project already uses - stops at Java 17, and its own team says a Java 21 runtime is "planned
for later this year" as of 4.3 (April 2026). What does exist, on GitHub, is **OpenJDK compiled to
WebAssembly**: the `openjdk21` recipe in `wangyenshu/recipes` (emscripten-forge) with its
`openjdk21-kit` launcher. That is a real JVM with a real class loader in a page - which is the only
thing that can give Fabric *at play time* on a modern version. It has three costs, all named below.

## The four routes, measured

| Route | Java ceiling | Class loader (i.e. Fabric) | Speed | State today |
| --- | --- | --- | --- | --- |
| **CheerpJ** (in the page) | **17** - `cheerpjInit({version: 17})` | yes, a real JVM | good (JIT to JS/wasm) | 1.0 - 1.12.2 work; 1.13+ needs our JS LWJGL 3; Fabric reported hanging (below) |
| **OpenJDK Zero → wasm32** (in the page) | **21** now, 25 by porting the recipe | yes, a real JVM | **slow**: interpreter only, no JIT for wasm32 | recipe, kit and link script exist; no Minecraft build yet |
| **AOT compile** (TeaVM, what Gaius and our workspace do) | any (it is a compiler, not a runtime) | **no** - mods are baked at build time | fastest | 26.2/26.3 build today; this is how the newest snapshots can run this week |
| **CheerpX** (a Linux VM in the page) | whatever the guest installs | yes | emulated x86, then a real JVM on top | not measured here; the heaviest of the four |

Two facts decide everything else:

* **Java version is a hard wall per route.** A 26.x client is class file 69 (Java 25), and no runtime
  that tops out at 21 will load it. 44 + javaVersion is the rule, and it is in
  `tools/aot_profile.py` so the pipeline can say which route a version needs from its own metadata.
* **Mods need a class loader.** Fabric's whole mechanism is transforming bytecode as classes load, so
  it needs a VM that loads classes at play time. A compiled client has none - which is why on the AOT
  row mods go in *before* the compile, applied by a real Fabric Loader running in the build. That is
  already implemented in this project (`mods/loader.py`, `mods/build_modded_workspace.py`,
  `mods/loader-src/loader-mod`).

## The Fabric question, answered with a citation

There is an open report that **Fabric Loader's boot hangs inside its ASM transformation under CheerpJ**
(`leaningtech/cheerpj-meta#231`, July 2026, with a minimal reproduction at
`xuishimm/cheerpj-fabric-hang-repro`). It hangs *before* LWJGL is touched - so it is not the graphics
shim's fault - and the vendor's reply is that Minecraft 1.16.5 "cannot work in any case since it depends
on LWJGL3, which cannot yet be compiled to WebAssembly via our toolchains", and that they will not look
at the hang in the short term.

So the project's plan no longer promises Fabric wherever a JVM exists. Every plan now carries a
`caveats` list, and the launcher shows it before the play button:

* on the CheerpJ row: Fabric is unproven, vanilla is not;
* on the shim row: the same report, plus the missing LWJGL 3;
* on the AOT row: mods are applied at build time, and only mods that survive ahead-of-time compilation
  bake in at all.

## What the open-source route actually gives us

`openjdk21` (emscripten-forge recipe, OpenJDK 21.0.10, Zero interpreter, built with `x11-wasm` for
AWT/Swing) plus `openjdk21-kit` (launcher, link script, page shell) means:

* a **real JVM**: `System.loadLibrary`, JNI, reflection, class loading, and therefore Fabric's mixins.
  Threads are real (pthreads + `SharedArrayBuffer`; the demo pages ship a COOP/COEP service worker so a
  static host can serve it).
* **native methods are static symbols.** There is no dynamic loader: `os::dll_lookup` is answered from a
  table named `emscripten_static_symbols`, generated by `gen-symbols.sh` from the archives you link in.
  That is the same idea as this project's CheerpJ natives (`cheerpjInit({natives: {...}})`) and the same
  idea as the loader's own report native - a name → implementation table - so the shape is already
  familiar in this repository, and `tools/lwjgl3_surface.py` already measures exactly which names are
  needed (458 members across 1.13 - 1.20.4, from real clients).
* **the graphics stack exists in emscripten.** `-sUSE_GLFW=3` (GLFW 3 on the canvas, with input),
  `MAX_WEBGL_VERSION=2` (GLES 3 emulated on WebGL 2, which is why 1.13+ maps so well onto WebGL2), and
  `libal` (OpenAL) is a system library. What is missing is the JNI layer mapping LWJGL's expected
  symbols onto those three - C work, mechanical, and *ours* to generate from the measurement.
* **a JDK 25 port is a version bump** of a recipe that already exists, not a research project: Zero
  builds on any platform the C toolchain reaches, and the patches in that recipe are about the C
  library and AWT, not about the Java version.

What it does not give: speed. Zero is an interpreter, so the compiled rows stay ahead of it - this is
the route for *correctness and mods*, not for frames per second. Say so on the card, not in a footnote.

## The order this lands in

Each step is verifiable, and the first two do not depend on the runtime existing at all.

**The AOT row (this is what "supports the latest snapshot" means today):**

1. **A version profile for any version, including the newest snapshot** - done:
   `tools/aot_profile.py` reads Mojang's document (java, sha1s, asset index), reads `version.json` out of
   the client jar (protocol, world, pack versions - no JVM needed), computes the class file version, and
   copies the *port's own* fields from the nearest existing profile while saying out loud which ones
   those were. `tests/test_aot_profile.py` pins the split.
2. **A loading screen that looks like the game** - done: `site/boot/shell.html` reproduces what the game
   itself draws (black, centred progress text, the game's 200x2 bar, its GUI scale, a pixel shadowed
   font), and `tools/aot_shell.py` puts it in front of a compiled client, removes that client's own
   splash by id, and hands over on the first OpenGL draw call - so no engine has to cooperate.
3. **Fabric mods, baked** - already implemented here, and the plan now says so instead of implying
   runtime mods.
4. Then one build per version, which is the 45-minute job in `build-snapshot.yml`; a snapshot needs a
   profile (step 1) and whatever source overrides that version's client needs.

**The wasm-JVM row (this is what "a loader that runs Java 25" means):**

5. Build the JDK 21 wasm runtime from the recipe (`pixi`/`rattler-build`, published to a conda channel
   for wasm32), link it into a page with the kit, and prove `java -version` in a browser.
6. Port the recipe to JDK 25, and prove a class file 69 loads.
7. Generate the LWJGL 3 JNI layer in C from the measured surface, over emscripten's GLFW 3 + GLES 3 +
   OpenAL, and prove a first frame (the same milestone the CheerpJ shim is chasing, on a different
   runtime - and this time the native call path is `ffi_call` into wasm, not a JS bridge).
8. Put **our own loader** on its classpath: `webmc.loader.WebMcLoader` is Java 8 bytecode, so a Java 25
   JVM loads it unchanged, and the link kit takes a classpath and a main class - which is exactly the
   interface it needs. Then Fabric Loader, then a mod jar.
9. Only then: is it fast enough to be worth offering next to the compiled row? Measure before claiming.

## Building the newest snapshot, today

The AOT row is a build system, and a build system can be pointed at a version nobody has ported yet.
That is what `.github/workflows/build-snapshot.yml` does, on a tag (`build-*`) or by dispatch:

```sh
git tag build-latest-snapshot && git push origin build-latest-snapshot     # or the Actions button
python3 tools/snapshot_status.py --log 40                                  # read what happened, from git
```

1. **The version is Mojang's own answer** - `latest-snapshot` in the default, so a new snapshot needs no
   edit here.
2. **`tools/aot_snapshot.py` prepares it**: the profile (from Mojang's document plus the `version.json`
   inside the client jar: protocol, world and pack versions, class file 69 for Java 25), the previous
   version's source overrides as a starting point, and a bring-up list seeded from its neighbour.
3. **`tools/aot_fixups.json` patches what the snapshot broke.** A snapshot changes the client's API, so
   the engine's browser code stops compiling in a place or two; each breakage is one entry with the
   exact text, what it becomes, the version it applies from, and why. A moved anchor is a refusal, not a
   skip.
4. **The build runs the engine's own scripts** (fetch, remap, overlays, release) with the bring-up list
   allowed, and `BRINGUP_SKIP` lines are recorded, so "it built" can never quietly mean "it built with
   half the patches off".
5. **Our boot screen goes in front**, the engine's own loading UI comes out, and the client is published
   as a **download** (never served as a page - see COMPLIANCE.md).
6. **Every attempt writes its report and log tail to a `build-log` branch.** No token, no web UI:
   `tools/snapshot_status.py` reads it, which is how the fixups above were written.

### How far the loop got, and where it stopped

Four attempts on 2026-10-14, each about ten minutes, each visible in the `build-log` branch:

| Attempt | Stopped at | What it took to fix |
| --- | --- | --- |
| 1 (38543240894) | `BrowserOpenGL.java:7095: error: visible has protected access in AbstractWidget` | a fixup: 26.4 made the field protected; use `isVisible()` |
| 2 (38545663119) | `Patch MinecraftClientPatcher.patchBuiltInRegistriesBrowserStartupYield failed ... and is not listed in the bring-up list` | a bring-up entry: 26.4 rewrote `BuiltInRegistries.createContents`, so the patch's anchor is gone |
| 3 (38547975838) | `Version profile check failed: client protocol version 1073742166 does not match 342` | reverting a "fix" of mine: the engine compares the profile against the client's raw protocol, marker and all |
| 4 (38549140842) | `ModernSymbols: inconsistent client jar ... 26.2 render class com/mojang/blaze3d/pipeline/RenderPipeline is still present next to renderpearl` | **nothing: this is engine work** |

Attempt four is the honest ceiling of this approach. **26.4-snapshot-4 replaced the render layer**:
`com/mojang/blaze3d/pipeline/RenderPipeline` and `ShaderSource` are gone in favour of
`com/mojang/renderpearl/api/pipeline/*`, `GlslCompiler` moved, and `VertexFormat` changed shape. The
engine's symbol prober detects the new renderer and refuses a jar that contains both, which is what its
26.3 patch chain produces on a 26.4 client. A browser patcher for renderpearl is a real porting job by
somebody who knows that renderer - and everything a *generated profile* can supply (java level, protocol,
pack versions, sha1s, source overrides, bring-up entries) was already supplied before that error.

So the snapshot path is automated and stops at a named wall, and `ports.json` records it as a blocker on
the 26.4+ range rather than promising a build. The newest *release* - which that engine does support -
goes through the same job (`.github/workflows/build-snapshot.yml` with `latest-release`).

### What preparing a version taught about whose data is whose

Two of the five attempts failed on a *fact*, not on code, and both are worth knowing before wiring any
of this up:

* **The engine owns how, Mojang owns what.** The engine's own 26.3 profile carried an asset-index hash
  that Mojang has since re-published, and the engine's check refused the build in two minutes. Keeping
  the engine's profile is right for `patchSet`, `extraPatchers` and `storage` - decisions about how to
  build that version - and wrong for `protocolVersion`, `packVersions` and the sha1s, which are facts
  about the version. So a generated profile is *merged* into the engine's, and the report says which
  fields changed.
* **A snapshot's protocol number keeps its high bit.** `0x40000000 | 342` is `1073742166`, and the engine
  compares the profile against exactly that. "Tidying" it to 342 fails the check, which is a good thing
  for a validator to catch and an embarrassing thing for a generator to do.

## Our own engine: the versions nobody licensed covers

The borrowed engines cover 1.7.10, 1.8.x, 1.13–1.14.4 (unlicensed, used deliberately — see CREDITS.md) and
1.21.11 / 26.2 / 26.3 (MIT). Nothing covers **1.16.5 – 1.20.4**, and nothing will cover **26.4+ snapshots**
until somebody ports the new renderer. Those are ours to write, on **TeaVM** (Apache-2.0, so no licence
question) — and the point of building it ourselves is that it is the version-coverage engine, not one more
borrowed tree.

### The ladder

1. **Toolchain proof** (days): compile a trivial app to wasm with TeaVM, host it with our boot screen, and
   prove the page shell, the packaging and the credits/branding path. No Minecraft.
2. **1.16.5 first** (weeks): Java 8, LWJGL 3.2, the simplest modern renderer of the uncovered range, and the
   version with the largest Fabric mod base. The work is mechanical and already measured:
   * decompile/remap the official client (Mojang publishes official mappings from 1.14.4 on, which is what
     makes 1.16.5+ a legal, repeatable target rather than a guess);
   * replace what a browser does not have — windowing/input (GLFW), GL (GLES-over-WebGL), audio (OpenAL),
     filesystem, network — as Java classes the client's own calls land on. `lwjgl3-webgl/surface/` already
     contains the measured member list per version, which is the work order for this step;
   * compile with TeaVM (`wasm-gc`), package one HTML, put our boot screen in front of it.
   Success is a title screen; then in-game.
3. **1.18.2 / 1.19.4 / 1.20.4** (repeat, cheaper): the same shape, Java 17, mostly reused patches.
4. **Our own mod bake**: apply Fabric mods at build time (the loader in `mods/` already plans, prunes and
   hooks a mod set) so the mods folder works on our own engine too — `mods/mods.json` is the manifest either
   way.
5. **26.4+ and the snapshots**: the renderer is the hard part and it changes when Mojang changes it. Nothing
   about this ladder makes that cheap; it makes it *ours*.

### Pre-releases, snapshots and the rest

They are not a special case in this pipeline: `tools/plan.py`, `tools/jvm_route.py` and
`tools/aot_snapshot.py` all classify by the version's own metadata (date, Java level, LWJGL generation), so
a snapshot routes exactly like the release it leads to and a new one needs no edit here. What it needs is an
engine whose patches match that client:

| Era | Today | With our own engine |
| --- | --- | --- |
| Indev / Alpha / Beta | real Java (CheerpJ) — attempts, pre-shader GL is unverified | unchanged: they are Java 8-era, so they fit the same engine shape if needed |
| 1.0 – 1.12.2 + snapshots | ✅ real Java, mods at play time | unchanged (no compile beats a compile) |
| 1.13 – 1.14.4 + snapshots | borrowed 1.14 workspace | our engine replaces it |
| 1.16.5 – 1.20.4 + snapshots | ❌ nothing | **the ladder above** |
| 1.21.11 / 26.x releases | MIT engine (vanilla only) | our engine adds the mods |
| 26.4+ snapshots | ❌ renderer | our engine, after the renderer port |

## How a mod set would reach a compiled 1.21.x client

The mods folder works at play time on the 1.0 - 1.12.2 row (a real JVM is running). On a compiled row
there is no class loader afterwards, so a mod has to be inside the client before TeaVM sees it. Three
routes, in the order worth trying, and the engine decides which are open:

1. **The engine's own patch chain** (the Gaius row). Its patchers are Java tools that rewrite the client
   before the compile (`dev.gaius.tools.*Patcher`, driven by `extraPatchers` in the version profile), and
   the engine compiles the client's decompiled sources plus a per-version override tree. A mod set can go
   in the same way a patch does: an overlay **sourced from the mod**, plus a generated patcher that calls
   the mod's entrypoint from the client's init. `mods/build_modded_workspace.py` already plans, prunes and
   hooks a Fabric mod set for the workspace lineage - the work here is a generator that emits *this*
   engine's patcher instead of that lineage's hook file, plus the classpath wiring so the mod's classes
   are compiled into the client.
2. **Our own engine**, where the hook layer is ours from the start: the mods manifest in `mods/` is
   already the input, and the bake is a step in the same pipeline (`mods/loader.py` is the reference for
   what the bake has to do: read `fabric.mod.json`, prune mixins whose target is not in this client,
   shim the Fabric API modules the set uses, generate one entrypoint call per mod).
3. **The real-JVM rows instead**, for anyone who wants Fabric *at play time*: 1.12.2 and older today, and
   1.13 - 1.20.4 once the LWJGL 3 shim draws a frame. Those are the versions where "drop a jar in and it
   loads" is true rather than baked.

What none of them can do: a mod with native libraries, one that generates bytecode at runtime, or one
whose mixins rewrite a class in a way the ahead-of-time compiler cannot see. The scanner says which of
those a jar is (`mods/portscan.py`) before a 45-minute build finds out.

## What this project will not do

* **No streaming.** A session on a server is a different product, and running one on CI is what got an
  earlier account suspended.
* **No prebuilt clients from other projects.** Linked where they live, never copied.
* **No pretending.** A route with no build is not offered as playable: the wasm-JVM engine is in
  `ports.json` with `"enabled": false` and its three blockers written down, so the plan can explain the
  route without promising it.
* **No game files in the repository**, on any of these routes: the client is fetched at build time by
  the person building, and a built client is published as a download rather than served as a page (see
  `COMPLIANCE.md`).
